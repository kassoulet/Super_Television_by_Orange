# stv - reverse-engineering log
## Unpacking (done)
- demo.exe = MZ stub + PMODE/W **1.20** (entry 0x59, MZ image 0x261b bytes, header SS=0x340; b-hyper/inside are 1.33/1.22 with entry 0x5e). `unpack_pmodew.py` (copy of b-hyper's, entry via env ENTRY) runs the stub under Unicorn:
  `ENTRY=0x59 python3 unpack_pmodew.py 80 ../demo.exe 0x261b 0x340 mem.bin` (needs the user-site unicorn, so no python -I). The loader reads the whole EXE, switches to PM and starts the program, which opens 'data.dat' (the fake DOS returns the EXE for any name; harmless, the dump is taken when the program exits).
- `mem.bin.gz` = raw 64 MB dump (gunzip to use). `image.bin` = linear 0x100000.. (program, Watcom CRT strings visible), `low.bin` = linear 0x10000.. (low object / loader area, a second copy of strings lives here), `image.dis` = objdump -M intel, VMA 0x100000.
## Phase 1 findings
### Program structure
- Entry (Watcom `_cstart`) 0x4ab5c, flat 32-bit, DS limit 64 MB (int21 ah=4a). PHAR int21 ah=30 returns eax=0x44580005, ebx=0x34; PSP selector 0x24 via LDT.
- main calls 13 effect routines in sequence (call sites 0x1c2f9..0x1c449; routines 0x45a30, 0x4705f, 0x476b4, 0x485b0, 0x4917b, 0x495c1, 0x47f86, 0x48209, 0x4856a, 0x4a186, 0x4a62f, 0x47d60, 0x47e79). Effect 8 (0x4856a) falls into effect 3's body (0x485b0), same engine, other assets.
- **The demo is synchronised to the S3M**: the player tick (0x3d980) keeps order/row in `[0x44505]` (word = ORDER index), `[0x44504]` (byte = row), `[0x44507]` (word = pattern), speed `[0x44502]`. Effects wait on `cmp [0x44505],N` (ex: effect 6 waits order 22) and flash/fade on specific rows (effect 6: rows 3,5,7,9,0xc,...). The ISR (0x45f1e, IRQ0 70 Hz) also advances fades/animation counters keyed on the order.
- Sound: custom S3M player (card 0 silent / 1 GUS / 2 SB / 5 SB16); flag `[0x4dacc]` = "no card" (the harness clears it at 0x1c2b8: card 0, player never ticks).
- Video: Mode X / unchained 320x200 (and chain4 mode 13h for the image effects), triple page flip (start 0 / 0x5355 / 0xa6aa), DAC palette uploaded with `rep outsb` (28 sites, rep_outsb.json: Unicorn cannot hook OUTS so these are patched).
- Files: data.dat (whole file read into memory once at 0x44cc4; `0x44c9a(eax=chunk, edx=dest)` is just a memcpy of chunk eax). anim2.dat and tnldata.dat are named in the binary but never opened in this run (no OPEN logged), fine.
### data.dat (solved)
29 dwords at 0x4dad8 (offsets relative to the file end, memcpy sizes = difference of neighbours). `assets/00..27.bin` = extracted chunks, `assets/png/` = RIX3 ('RIX3', w, h, flag, 768-byte 6-bit palette, 8-bit pixels) converted: 06,10,15,17,19-22,24-27. Chunks used per effect are in golden/log.txt (last line).
### Harness (re/emu.py + re/golden_run.py)
- emu.py (Unicorn): DOS int21 (file I/O), int10, int16, DPMI int31 (arena 0x20000000), planar VGA shadow + CRTC/sequencer/GC + DAC palette, virtual clock (instrs/IPS + warp on port 0x3da polls), IRQ0 injected every 20000 instrs at the PIT rate. Bugs fixed this session: handle was read from the full EBX (upper garbage) so data.dat was never read into memory (all earlier "effects" were drawn from zeros: flat colours); palette*255 overflowed in uint8 (black frames).
- `golden_run.py OUTDIR [IPS=1e6] [EVERY=5] [TMAX=260]`: runs the WHOLE original once (~5 min wall at IPS=3e6, ~2 min at 1e6 but CPU-heavy effects are then starved). The S3M player is not run: the sync variables 0x44504/5/7 are written from `s3mtime.json` (order/pattern/row from `s3mtime.py makako.s3m`, copied from the megademo agent; no tick routine called, so speed/tempo effects such as Zxx are not modelled). Music t=0 = entry of effect 0. Saves per EVERY music-seconds the brightest of 0.2 s-spaced display() samples (beat flashes would be missed otherwise) -> golden/mTTT.png (+ golden/log.txt, contact.png).
- Not bit-exact: frames depend on IPS (loop pacing, warp) and on the music clock being a model; they are reference pictures, not a pixel-diff oracle yet. Speed was fine, the VGA hook optimisation was not needed.

### Flaky uitest, root cause (session 5)
- Race in web/player.js: draw() started load(i) without keeping the promise, and only the rAF loop redrew a paused player after a load; if the load finished between two frames, the placeholder stayed on screen. load() now caches one promise per effect and draw() redraws when its own load resolves (if the effect is still current).
- The 'fx07 at 156 s blank' was not a race: 156 s lies between two flashes of fx7 (fade 0, black palette, a pure function of t). The old test passed only because the 'not ported' placeholder counted as non-black. The test now seeks to 153.1 s (just after the first flash row). fx9/fx10/fx11 failures were the same placeholder race. 5 runs in a row: all PASS, no exceptions.

## Original player clock (session 8, derived from 0x3d980 / 0x3dde9 / 0x44216)
- The original has NO PIT-driven music clock. It is sound-card driven: [412ed] = mixing rate in Hz (default 0x61a8 = 25000 at 0x41c8b; the SB driver 0x44216..0x4425e rewrites it to 1e6/(1e6/rate), the effective rate), [44501] = tempo (init 0x7d, S3M T command), [44502] = speed.
- Per tick 0x3dde9: samples = ((rate<<8)*5/tempo)>>1 in 8.8 fixed point; low byte accumulates in [2a582] with carry (adc) into the integer part [2a57e] = samples mixed for this tick. So a tick = 2.5/tempo s up to 1/256 sample, a row = speed ticks (+ SEx delay), 0x3d980 `inc [3d8b3]`, latch row/order/pattern when it equals speed. The mixer fill is the only tick source, so on hardware the row clock is the audio sample clock.
- Check (python, TT = (ticks,tempo) per row from s3mtime.py walker, 2400 rows): the original formula with rate 22050/25000/44100 equals s3mtime.model.json within 0.7 ms at every row (rate independent, 1/256 carry). libopenmpt (s3mtime.json) truncates samples/tick to an integer, so it runs 0.1375 s fast at the end (251 s), growing linearly (0.55 per mille). Not a model error: ~14000 ticks * 0.5 sample * 22.7 us.
- Decision: timeline.js stays on libopenmpt times, because the audio is libopenmpt and the original keys every scene on (order,row), so visuals stay locked to the rows actually heard. The original's own clock would put row starts up to 0.1375 s later at the end of the demo; inside one effect (<= 40 s) the difference is <= 22 ms (half a frame). The harness (re/fx_oracle.py) uses libopenmpt rows with IRQ0 (PIT 70 Hz, independent of the sound card) for effect pacing, which is why pacing constants (NINIT, EXIT, TPF) are PIT-tick counts, not music time.
- Why the PIT tick count and the music row are unrelated clocks in the original: effect ISRs run on IRQ0 (70 Hz), the player on the sound-card IRQ. Real-machine phase between them (hence NINIT/EXIT/TPF) is machine dependent and cannot be derived: stays UNRESOLVED/machine-dependent, not a port error.
