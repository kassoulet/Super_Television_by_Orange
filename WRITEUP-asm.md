# SUPER TELEVISION (Orange, 1996) - asm snippets worth reading

All addresses are linear addresses of the unpacked program (`DEMO.EXE` = PMODE/W 1.20 stub + Watcom C 32-bit flat model; the guest memory is dumped by `re/unpack_pmodew.py`,
`re/low.bin` = linear 0x10000.., code at 0x3a000..). Every listing was produced with `objdump -D -b binary -m i386 -M intel --adjust-vma=0x10000 re/low.bin` (capstone is not installed
here, so objdump stands in; same decoder role) and the addresses match the hooks used with the Unicorn oracle (`re/fx_oracle.py`). Watcom convention: arguments in EAX, EDX, EBX, ECX.

The code is a 486/Pentium-era mode X demo: no MMX, no SSE, no x87 in the effects listed; integer tables and 16-bit register tricks. In the effect routines examined I found
**no self-modifying code** (all stores to the code segment I saw, `cs:` prefixed, are in the extender/loader area below 0x11000); the tricks are about table layout, register halves, SWAR and VGA registers.
(The runs of `nop` after conditional jumps, e.g. at 0x47e38 or 0x4a018, are compiler alignment padding.)

## 1. Table lookup by 16-bit wraparound (fx1, 0x46d53)

```
46d53: mov cl,0x64              ; 100 rows
46d59: mov eax,[0x56254]        ; table base, 64 KB aligned: ax is now free
46d5e: mov ch,0x40              ; 64 pixels per row per plane
46d60: cmp byte [ebp+0],0       ; background mask: skip if not 0
46d64: jne 0x46d88
46d66: mov ax,[esi]             ; the "map" word of this pixel
46d69: mov dl,ah                ; edx/ebx are 0 above: byte -> index
46d6b: mov bl,al
46d6d: add ax,[0x554f0]         ; + global sine offset
46d74: add ax,[edx*2+0x562b5]   ; + T1[map>>8]
46d7c: add ax,[ebx*2+0x564b5]   ; + T2[map&255]
46d84: mov al,[eax]             ; colour = TBL[(sum) & 0xffff]
46d86: mov [edi],al
```
Why it is clever: `eax` holds an aligned 64 KB table pointer, so **`ax` is the 16-bit offset**. Three 16-bit adds accumulate the displacement and the carry out of bit 15 is simply lost: the lookup wraps
inside the table with no `and`. The two 256-word tables are indexed by the two bytes of the same word (`dl=ah`, `bl=al` with `xor edx,edx / xor ebx,ebx` hoisted at 0x46d55), so the per-pixel work is 4
loads + 3 adds, no multiply. `esi += 8`, `ebp += 4`, `edi += 1` per iteration: the source is read at stride 8 because mode X plane p only holds x%4 == p, and the routine is called 4 times
(`0x46da9`) with `out 0x3c4` plane masks 8, 4, 2, 1 between calls. Port: `half()` in `web/fx/fx01.js`.

## 2. Replacing half a pointer with a byte: the lens (fx2, 0x47626..0x4768e)

```
47672: xor bh,bh
47674: mov al,[esi]             ; texture window 1
47676: add al,[ebp+0]           ; + window 2   (al = t1+t2, mod 256)
47679: mov ah,[0x5ca7e]         ; row counter 0x1c+y
4767f: mov dh,[eax]             ; dh = LENS[row][al]
47681: mov ah,ch                ; ah = x
47683: mov dl,[eax]             ; dl = LENS[x][al]
47685: mov bl,[edx]             ; bl = PICTURE[dh:dl]
47687: mov bh,al
47689: shr bh,2
4768c: mov al,[ebx]             ; out = SHADE[(al>>2):bl]
4768e: mov [edi],al
```
`eax`, `edx` and `ebx` each carry a 64 KB-aligned base (the loader aligns them: `or eax,0xffff / inc eax` at 0x4770a, 0x476bf, 0x47725, and chunk 6 is copied to such an address), and the
code only ever overwrites the **low 16 bits with two byte moves**. `mov dh,[eax] / mov dl,[eax]` builds a 2D coordinate pair `(dh,dl)` directly as a 16-bit index with no `shl/or`; `al` is at the
same time the *data* of the previous step and the *address low byte* of the next, a three-level dependent lookup in 10 instructions. The lens table is generated by a tiny loop (0x476dd..0x476f9):

```
476e4: mov eax,ebx / imul eax,edx / sar eax,8 / add al,0x80 / mov [edi],al   ; ((row-128)*(256-col)>>8)+0x80
476f1: dec edx  (col 256..1)   476f6: inc ebx (row -128..127)
```
Because the pair is a raw offset into the **file image of chunk 6** (header and palette included), the port indexes the whole file (`C6[(dh<<8)+dl]`) to stay exact.

## 3. Four pixels per dword, with 16-bit pointer registers for the wrap (fx5, 0x4971f..0x49777)

```
49738: dec si                   ; left   (16-bit ops: wrap inside the 64K block)
4973a: inc bx                   ; right
4973c: add bp,0x100             ; down
49741: sub dx,0x100             ; up
49751: mov eax,[esi]
49753: add eax,[ebx]
49755: add eax,[ebp+0]
49758: add eax,[edx]
4975a: shr eax,2
4975d: and eax,0x3f3f3f3f
49762: mov [edi],eax            ; 4 blurred heights at once
49764: add si,4 / add bx,4 / add bp,4 / add dx,4
```
The box blur of the height map processes **4 neighbours x 4 pixels with one dword add each**: since the heights are < 64, the sum of four bytes never carries into the next byte
(max 4*63 = 252), `shr 2` moves bits from byte k+1 into byte k and the `& 0x3f3f3f3f` removes them. Neighbour pointers are kept as `esi/ebx/ebp/edx` whose **low halves are stepped with 16-bit instructions**
(`add si,4`), so the image edge wraps inside its 64 KB block for free. The known cost: the dword reads at offsets 0xffff/0xfffd run 3/1 bytes past the block (the port uses zeros there, UNRESOLVED on real hardware).
The same block is reused 4 times by swapping the two buffers (`xchg [0x60778],eax` at 0x4977f). The slope table that follows (0x497b7) is a 2-instruction-per-axis trick: `sub al,[ebx]` and `sub ah,[ebp]` leave the
two signed differences in the two halves of `ax`, `shl al,2 / shl ah,2`, one word store: **a 2D vector in 16 bits**. The per-frame inner loop (0x49590) uses it:

```
49590: mov dx,[esi]             ; w  (screen->uv word, edx high = chunk10 base)
49593: mov bp,dx
49596: add dx,[0x60ffc]         ; + OFF  (16-bit: wrap)
4959d: movzx ebx,dx / shl ebx,1
495a2: mov cl,[edx]             ; texture colour
495a4: add ebx,[0x609ee]        ; D table (words)
495aa: add bp,[ebx]             ; w + slope   (both axes in one add)
495ad: mov ch,[ebp+0]           ; light-map shade
495b0: mov al,[ecx]             ; SHADE[ch:cl]
495b2: mov [edi],al
```
One bump-mapped pixel = 11 instructions with no multiply: the **u,v coordinate packed in one 16-bit word** is displaced by a packed slope with a single `add bp`.

## 4. SWAR feedback and a free palette index (fx4, 0x4914a..0x49177)

```
4914a: mov eax,[esi]            ; D: 4 displaced pixels
4914c: lea eax,[eax+eax*2]      ; 3*D
4914f: add eax,[ebx]            ; + C (constant picture)
49151: shr eax,2
49154: and eax,0x3f3f3f3f       ; (3D+C)/4 per byte -> new feedback T
49159: mov [ebp+0],eax
4915c: shr eax,2
4915f: and eax,0x0f0f0f0f       ; level -> low nibble
49164: or  eax,[edx]            ; | (logo pixel << 4), prepared once
49166: mov [edi],eax            ; 4 VRAM pixels
```
`lea [eax+eax*2]` is the cheap x3. The same value gives the recursion state (6 bits) and, shifted again, the 4-bit brightness that is ORed with a **pre-shifted** copy of the other picture (chunk 15 is
`<< 4` at load, see the port's `O=...map(v=>v<<4)`). The palette is then built as a 16x16 table (`0x4931f`), so no per-pixel colour arithmetic is needed. The 3/4-1/4 mix means an error decays by 3/4 per frame (why the port must replay from the first frame). The distortion
read before it (0x49106..0x49114) builds two bytes into `ax` from two table lookups and stores them with one `mov [edi],ax`: `edx = [ebp]+ebx` (X offset + row offset), `al=[edx]`, then `[ebp+4]` for the next pixel.

## 5. The bump gradient as a table of dword offsets (fx10, 0x4a50d..0x4a533 and 0x4a4b4..0x4a4c5)

```
4a4b4: mov eax,[esi]            ; 4 windows of the texture, each a dword (4 pixels)
4a4b6: add eax,[ebx]
4a4b8: add eax,[edx]
4a4ba: add eax,[ebp+0]
4a4bd: shr eax,2
4a4c0: and eax,0x3f3f3f3f       ; average of 4 moving crops, 4 pixels at a time
...
4a50d: mov al,[esi+0x280]       ; HB[i+640]  (HB rows are 160 bytes: 4 rows down)
4a513: sub al,[esi-0x280]       ; dy
4a519: movsx eax,al
4a51c: mov bl,[esi+4]
4a51f: sub bl,[esi-4]           ; dx
4a522: movsx ebx,bl
4a525: neg eax / neg ebx
4a529: lea eax,[eax+eax*4]      ; x5
4a52c: shl eax,6                ; x64  => x320
4a52f: add eax,ebx
4a531: mov [edi],eax            ; offset into the second texture
```
`5 * 64 = 320`, one scanline of the second picture, obtained with `lea`+`shl` instead of `imul`: **the gradient is already a memory offset** (-dy*320 - dx), so the final pass only does `OR texture[s + G]`.
Heights are 0..15 (chunks 19/20 have 16 colours), so the byte sums are safe from carries exactly as in snippet 3. The final blit (0x4a56b) writes two pixels of a 2x2 block per iteration and reuses the low nibble:

```
4a596: mov al,[edx]             ; HB (height)
4a598: or  al,[esi+ebp]         ; | chunk20[s+G]  (pre-shifted <<4 at 0x4a74d: lods / shl al,4 / stos)
4a59e: mov [edi],al
4a5a0: and al,0x0f              ; keep the height nibble only
4a5a2: or  al,[esi+ebp+0x141]   ; | the other texel (+321: next row, next pixel)
4a5ac: mov [edi+0x141],al       ; second pixel of the block
```
Two alternating routines (`0x4a56b` writes +0x141, `0x4a5cb` writes +0x13f) fill one diagonal per frame; the choice flips with `[0x6bcbd]` (0x4a53a..0x4a565): half the pixel work per frame, the other half comes from the previous frame.

## 5b. fx11 - the whole transparency test is a compare and a skip (0x47e31)

```
47e31: mov al,[ebp+0]           ; text strip pixel
47e34: cmp al,0
47e36: jne 0x47e3e
47e3c: mov al,[esi]             ; else the picture pixel
47e3e: mov [edi],al
```
The scroll is only the start of `ebp`: `(n>>1)*320` (0x47e21..0x47e29: `sar ebx,1 / imul ebx,ebx,0x140`), `n` incremented by the ISR (`inc [0x5f498]` at 0x47e72).

## 6. The screen as the state: VRAM read-back through a 16-bit table (fx9, 0x49fce..0x4a0a0)

```
49fcc: mov ah,[0x6103e] / mov al,2 / out dx,ax   ; 0x3c4: map mask (write planes)
49fdc: mov ah,[0x6103c] / mov al,4 / out 0x3ce   ; GC index 4: READ MAP SELECT
4a025: xor ah,ah
4a027: mov al,[ebp+0]           ; random byte -> offset index
4a02a: mov edx,[eax*4+0x6527e]  ; one of {0,+-3,+-480}
4a031: mov al,[esi+edx]         ; image pixel, shifted by that offset
4a034: mov ah,[ecx]             ; ah = what is on screen NOW (VRAM read)
4a036: mov [ebx],al             ; the shifted image (next frame's source)
4a038: mov al,[eax+0x61072]     ; new = TAB[ah:al]  (VRAM, image)
4a03e: mov [edi],al             ; written back to the same address
4a04a: sub ah,0x40 ... add al,0x40   ; second scanline of the triplet: bank 1
4a065: sub ah,0x80 ... add al,0x80   ; third: bank 2
```
The effect needs `new = B[old] + A[img]` per colour channel; the code replaces the arithmetic with **one 64 KB table whose index is `ah:al`**, where `ah` is read straight **from video memory** (GC register 4 selects the plane; two passes read
planes 0 and 3 with different masks, 0x3ce/0x3c4 are set at 0x49fdc and 0x4a0a1). The three scanlines of one RGB pixel live in three palette banks (0, 0x40, 0x80); subtracting/adding the bank base around the lookup lets all three share one table.
Each loop iteration handles three scanlines, so the static is a **temporal low pass of the framebuffer** with no frame buffer in RAM. The random generator (0x4a2d9..0x4a2f8) is 8 instructions per dword:

```
4a2ea: stos [edi],eax           ; output the state
4a2eb: add eax,ebx / add ebx,edx
4a2ef: rol edx,2 / rol ebx,1
4a2f4: xor eax,edx / xor edx,eax
4a2f8: loop 0x4a2ea             ; ecx = 0x12c0 = 4800 dwords = 19200 bytes
```
`stos` + `loop` with the three state words in `eax,ebx,edx` and no memory traffic. Port: `step()` in `web/fx/fx09.js` (checked on 99 oracle dumps, 0 unexplained).

## 7. 8x8 bilinear patches drawn with VGA plane masks (fx3 0x48e0e, fx0 0x4679a)

```
48e0e: movzx eax,[0x5d28e]      ; corner C (bottom-left)
48e15: movzx ebx,[0x5d28c]      ; corner A (top-left)
48e1c: sub eax,ebx / shl eax,6  ; (C-A)<<6 : step per 2 rows, 8.8 fixed point
48e21: shl ebx,8                ; A<<8
  ...                           ; same for the right column (B, D)
48e3f: add ebx,0x8000 / add edx,0x8000   ; +0.5 rounding
48e50: mov [esi],bh             ; left  edge value of row pair i
48e52: mov [esi+1],dh           ; right edge value
48e55: add ebx,eax / add edx,ebp
...
48e64: out dx,ax  (0x3c4, ax=0x0502)     ; map mask 5 = planes 0 and 2
48e83: mov cl,bh / add ebx,eax / mov ch,bh / add ebx,eax
48e8b: mov [edi],cx             ; WORD store: pixels (x, x+2) get cl, (x+4, x+6) get ch
48e8e: mov [edi+0x51],cx        ; next row, shifted one byte: quincunx
...
48ea5: ... ax=0x0a02             ; map mask 0xa = planes 1 and 3, edi += 0xf0 (3 rows lower)
```
The byte of the 8.8 accumulator is read with `mov cl,bh`, **no shift**. With map mask 5 a byte store writes two planes at once, so a word store of `cx` colours **4 pixels (two at each of two x positions)**;
the second pass with mask 0xa fills the odd pixels, shifted down 3 rows with a different phase of the ramp (`shl eax,1` between steps). The whole 8x8 block is 4+4 word stores x 2, **16 stores for 64 pixels**, and the
x interpolation is done by the ramp value rather than per pixel. fx0's version (0x4679a) is the same patch, with the pass over planes 0/2 then 1/3 written as in `cell()` (`web/fx/fx00.js`). Port: `cell()` in `swirl.js`, plane arrays `V[p*65536+a]`.

## 8. A 3-instruction hash as the noise generator, and a crossfade by `imul`/`sar 11` (fx0, 0x46620..0x4668f)

```
46620: mov bl,al / and bl,0x3f           ; noise value = 6 bits of the state
46628: movzx edx,[edi]                   ; old buffer value
4662b: lea edx,[edx+edx*2]               ; *3
4662e: add ebx,edx / shr ebx,2           ; (new + 3*old) / 4   : temporal smoothing
46633: mov [edi],bl
46636: add eax,0x9d
4663b: rol eax,0xb
4663e: xor eax,0x9d                      ; next state: 3 instructions
...
4667f: imul eax,[0x4db68]                ; picture * w1
46686: imul ebx,[0x4db64]                ; noise   * w2    (w1 + w2 = 0x800)
4668d: add eax,ebx / sar eax,0xb         ; crossfade, then clamp to 0x3f (cmp / jle / mov eax,0x3f)
```
`add / rol / xor` with constant 0x9d is the whole PRNG; the smoothing reuses the `lea x*3` trick. The crossfade weights always sum to 0x800 (the ISR does `b64--, b68++`, 0x46603 gates on `b64 != 0`),
so `sar 11` is the division: **fades with no divide and no float**.

## 9. Separable warp: one add per pixel (fx0, 0x45136 and 0x452ee)

```
45176: mov eax,0xffffff60               ; -160
4517b: imul eax,edx                     ; -160 * (p+0x80)
4517e: add eax,0xa00000                 ; + 160<<16  (screen centre)
45183: add eax,[0x4dc4c]                ; + pan
45189: add eax,0x10000
 ...                                    ; loop 320x: ebx = eax>>16 clamped to [0,0x13f] -> X[i], eax += p
45302: mov ebx,[esi]                    ; Y[row] (already *320 + texture base)
45304: mov ebp,[0x4dc00]                ; X table (stride 0x10: plane p, column group)
4530a: mov edx,[ebp+0]                  ; X[x]
4530d: add edx,ebx                      ; address = X[x] + Y[y]
4530f: cmp byte [edx],0                 ; index 0 = transparent
45312: je 0x4531c
45318: mov al,[edx] / mov [edi],al
4531c: mov edx,[ebp+0x10] ...           ; next plane's pixel, same row
```
The zoom/pan is a 16.16 linear ramp `i*p`, clamped, evaluated **once per column and per row** (320 + 200 steps), not per pixel; both coordinates of the texture are folded into a single address by premultiplying the row table
by 320. A 320x200 rotozoom-free warp then costs a load, an add, a compare and a store per pixel. The X table is read at stride 0x10 (4 dwords) so that **one pass per plane** reads 80 columns. (An earlier note in `re/NOTES.md` about a 2-D pointer table with 0x500 stride was wrong: `add ebp,0x500` is dead code; corrected in session 9.)

## 10. VGA register work: mode X, vsync, DAC, page flip (helpers 0x49e9e..0x49f43, 0x4a317)

```
49ea2: mov dx,0x3da / in al,dx / test al,8 / je 49ea6        ; wait until the retrace bit is set...
49eab: in al,dx / test al,8 / jne 49eab                      ; ...then until it is clear   (0x49ecc / 0x49ede: the two half-waits)
49ef0: mov dx,cx / add cx,cx / add cx,dx                     ; count = 3 * colours
49ef9: mov dx,0x3c8 / out dx,al / inc dx / cld / rep outsb   ; DAC: one instruction uploads the palette
49f0c: mov ax,0x0604 / out 0x3c4,ax                          ; seq reg 4 = 6: chain-4 off (unchained / mode X)
49f1a: mov ax,0x0014 / out 0x3d4,ax                          ; CRTC 0x14: dword mode off
49f1c: mov ax,0xe317 / out dx,ax                             ; CRTC 0x17: byte mode on
4a317: mov al,0xd / mov ah,bl / out 0x3d4,ax ; dec al / mov ah,bh / out 0x3d4,ax   ; CRTC 0xc/0xd: display start address
4a376: mov eax,[0x61061] / xchg [0x61065],eax / mov [0x61061],eax        ; rotate page offsets
```
Notes: the vsync wait is done **before** the DAC upload (0x4a34d..0x4a359 then 0x4a35b..0x4a36f), so palette changes land in the retrace; `rep outsb` into 0x3c9 is the fastest DAC write on the 486 (Unicorn cannot hook it,
28 sites are patched in the harness, `re/rep_outsb.json`). Page flipping is two `out`s to CRTC 0xc/0xd with the page offset in `bl/bh`; the pages (0, 0x5355, 0xa6aa in fx0, 0, 0x7d00, 0x3e80 in fx1) rotate through `xchg` with memory. The effects write to `0xa0000+page`
with the **map mask** (`0x3c4` index 2) instead of computing planes in software.

## 11. Palette fades as an integer multiply with a clamp (all effects; fx6 0x4818e)

```
4816f: mov dword [0x5f48b],0x180        ; flash: fade = 1.5 on a row
48179: mov edx,[0x5f48b]
4818e: movzx eax,byte [esi]             ; 6-bit palette entry
48191: imul eax,edx
48194: sar eax,8                        ; * fade / 256
48197: cmp eax,0x3f / jle ...           ; clamp
481a0: mov eax,0x3f
481a5: mov [edi],al
481b9: sub dword [0x5f48b],0x10         ; decay 16 per vsync
```
The fade is 8.8 fixed point; values above 256 push colours past white (clamped at 63), which makes the flash look like over-exposure. The same pattern appears in fx10's palette (0x4a8a3: `imul` of two palette bytes, `imul` by the product scale, `shr 12`, `imul` by the fade, `sar 8`, clamp)
and fx9's (0x4a33e). Port: `setPal()` in `web/fx/common.js`.

## 12. The clocks: a PIT divisor for the effects, a fractional-sample tick for the music

```
1be1f: mov eax,0x1234de                 ; 1193182
1be29: idiv ebx                         ; / divisor passed in eax (0x4295 = 17045) -> 70.0027 Hz   (called from 0x1c2de)
1be2b: mov edx,0x36 ... out 0x43        ; counter 0, mode 3
1be46..1be61: out 0x40 (low), out 0x40 (high)
```
```
3dde9: mov cl,[0x44501]                 ; tempo
3ddef: mov ax,[0x412ed]                 ; mixing rate (Hz)
3ddf5: shl eax,8
3ddf8: lea eax,[eax+eax*4]              ; * 5
3ddfb: div ecx                          ; (rate<<8)*5 / tempo
3ddfd: shr eax,1                        ; samples per tick, 8.8 fixed point
3ddff: mov cl,al / shr eax,8
3de04: add [0x2a582],cl                 ; fractional part accumulates...
3de0a: adc ax,0                         ; ...and its carry adds one sample
3de0e: mov [0x2a57e],eax                ; samples to mix this tick
```
A tick is `2.5/tempo` seconds to within 1/256 sample, **without float**: the low byte of the 8.8 number is accumulated with `add`/`adc`, so tempo changes (Txx) never drift. libopenmpt truncates samples per tick, so it runs up to 0.1375 s ahead at the end (`re/NOTES.md`, "Original player clock": checked equal to the model within 0.7 ms at all 2400 rows, rate independent). The effects do **not** use this clock: their ISRs run on the 70.0027 Hz PIT tick and pace on port 0x3da, which is why their pacing constants are machine dependent. The effect routines wait for the music with plain compares (`cmp word cs:[0x44505],0x25` at 0x47e50 = "until order 37").

## 13. Per-effect ISR swap

The master (`0x1c2c8..0x1c449`) calls the 13 routines in sequence, and **before each call installs a new IRQ0 handler** (`mov ebx,0x1be94 ; mov eax,8 ; call 0x4adbb` at 0x1c30b..0x1c317, then `call 0x4705f` for fx1; fx2 0x1bebc, fx4/8 0x1bee4, fx5 0x1bf0c, fx6 0x1bf34, fx10 0x1bf5c, fx11 0x1bf84).
The wrapper `0x1be6a` saves everything (`pusha`, DS, ES, FS, GS) and calls the effect's tick, so an effect's whole animation state is **a handful of counters in its ISR** (`A += 0x20` etc.) and its main loop only renders from them. That is the property the port exploits: each ISR is ported literally (`isrStep`) and replayed from the entry to seek.
